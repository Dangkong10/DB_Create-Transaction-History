1 개요 · 핵심 변경 요약

비즈니스 목적

영수증 출력 후 당일 입금이 안 된 거래처의 미수금을 자동으로 다음날 영수증·집계표에 합산해 청구한다. 현재는 수기로 미수를 추적해야 한다.

핵심 변경 (한눈에)

  • 새 DB 테이블 1개 추가 (입금기록)
  • '영수증 출력' 페이지에 [입금 입력] 카드 추가 (모달 팝업)
  • 영수증·집계표 출력 시 전잔고 자동 채움 (출력 폼 변형 X)
  • '특정 거래처 영수증' 검색 동작 변경 (거래처명 입력 전엔 표시 X)
  • 플로우 안내 칩 4개의 아이콘 제거 (텍스트만)
⚠ 절대 변경 금지: 영수증·집계표 출력 폼의 컬럼 구조, 칸 위치, 디자인.
→ 기존에 비어있던 '전잔고' 칸과 영수증의 '공급가 총액' 윗 빈 칸만 자동으로 채움.

2 데이터 모델 (DB) — 실제 구현 ✅

⚠ 기획 시 가정 ↔ 실제 구현 차이: 초기 명세서는 가상의 MySQL/FK 모델로 작성됐으나, 실제는 Supabase (PostgreSQL) 환경. 기존 transactions 컨벤션에 맞춰 customer_name TEXT (FK 아님) + user_id UUID + RLS 정책 적용.

새 테이블 ① — public.payments NEW

-- 거래처별 입금 사건을 row 단위로 저장 CREATE TABLE IF NOT EXISTS public.payments ( id BIGSERIAL PRIMARY KEY, user_id UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE, customer_name TEXT NOT NULL, -- transactions와 동일 스타일 (FK X) payment_date DATE NOT NULL, -- 사용자 입력 (기본=어제, 미래 차단) amount INTEGER NOT NULL CHECK (amount > 0), created_at TIMESTAMPTZ NOT NULL DEFAULT now() ); CREATE INDEX IF NOT EXISTS idx_payments_user_id ON public.payments(user_id); CREATE INDEX IF NOT EXISTS idx_payments_user_customer ON public.payments(user_id, customer_name); CREATE INDEX IF NOT EXISTS idx_payments_user_customer_date ON public.payments(user_id, customer_name, payment_date); -- RLS 정책 4개 (SELECT/INSERT/UPDATE/DELETE) — auth.uid() = user_id

UNIQUE 제약 없음 — 같은 거래처에 같은 날짜로 여러 row 허용 (Q4).

마이그레이션 파일: supabase-migration-2026-05-payments.sql

새 테이블 ② — public.adjustments v1.2 NEW

-- 시스템 미수금과 실제 미수금 차이 보정용 (시스템 도입 전 잔액, 외부 거래 등) CREATE TABLE IF NOT EXISTS public.adjustments ( id BIGSERIAL PRIMARY KEY, user_id UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE, customer_name TEXT NOT NULL, adjustment_date DATE NOT NULL DEFAULT CURRENT_DATE, amount INTEGER NOT NULL CHECK (amount <> 0), -- 0 금지. +미수↑ / -미수↓ created_at TIMESTAMPTZ NOT NULL DEFAULT now() ); -- 인덱스 3개 + RLS 정책 4개 (payments와 동일 패턴)

마이그레이션 파일: supabase-migration-2026-05-adjustments.sql

기존 테이블 (변경 없음) KEEP

  • public.transactions — 거래내역 (1행 = 1품목). customer_name TEXT
  • public.customers — 거래처 마스터. name TEXT (FK 안 씀)
  • public.products — 품목. 단가 lookup
  • public.special_prices — 거래처별 특가
💡 거래처별 현재 미수금은 저장하지 않음. 매번 SUM 계산으로 도출. 매일 마감 갱신 작업 없음.

3 핵심 계산 공식 (v1.2 — 조정 반영)

① 현재 미수금 (입금 입력 화면 표시용)

현재미수금(거래처 X) = SUM(transactions.quantity × unit_price WHERE customer_name = X) − SUM(payments.amount WHERE customer_name = X) + SUM(adjustments.amount WHERE customer_name = X)

② 전잔고 (영수증·집계표의 '전잔고' 칸)

전잔고(거래처 X, 출력 날짜 D) = SUM(transactions.quantity × unit_price WHERE customer_name = X AND date < D) − SUM(payments.amount WHERE customer_name = X AND payment_date ≤ D) + SUM(adjustments.amount WHERE customer_name = X AND adjustment_date ≤ D)

③ 당일매출 (영수증·집계표의 '매출금액' 칸)

당일매출(거래처 X, 출력 날짜 D) = SUM(transactions.quantity × unit_price WHERE customer_name = X AND date = D)

④ 총잔액 (영수증의 '공급가 총액', 집계표의 '총잔액' 칸)

총잔액(X, D) = 전잔고(X, D) + 당일매출(X, D)

구현 위치

모든 계산은 lib/payments.ts 의 함수들로 캡슐화:

  • getAllOutstandings() — 모든 거래처의 현재 미수금 Map (입금 입력 모달용)
  • getCurrentOutstanding(name) — 한 거래처
  • getReceiptBalancesForDate(date) — 날짜 D의 거래처별 전잔고/당일매출/총잔액
  • getReceiptBalancesForCustomer(name, date) — 한 거래처용
  • savePayments(items[]) — 입금 일괄 INSERT
  • saveAdjustment(item) — 조정 INSERT
  • getPendingCustomers() — 양수 미수만, 가나다순
💡 adjustments 테이블 fetch 실패 시 (마이그레이션 미적용 등) → 자동으로 0 fallback. 앱 안 깨짐.

데이터 로딩

  • 모달 열림 시: 현재미수금 > 0 인 모든 거래처 조회 (날짜 무관)
  • 거래처 정렬: 기존 가나다순
  • 전체 미수 0이면 본문에 "정리할 미수가 없습니다" 안내

날짜 입력 동작

  • 기본값 = 어제
  • type="date", max=오늘 — 미래 날짜 차단 (Q3)
  • [어제] / [오늘] 빠른 버튼 제공

[전액 입금] 버튼 동작

  • 클릭 → 입력란을 현재미수금 값으로 자동 채움
  • 버튼 시각 변화: ✓ + 초록색. 사용자가 직접 수정하면 원상복구.

[저장] 동작

  1. 입력란이 비어있지 않고 > 0인 거래처만 저장 대상
  2. 입금금액 > 현재미수금 인 거래처가 있으면 경고 모달 (Q1):
    "거래처 X의 현재 미수금은 18,000원입니다. 입력값 180,000원이 더 큽니다. 정말 저장하시겠습니까? [취소] [확인]"
  3. [확인] 시 일괄 INSERT (트랜잭션). 음수 미수금 허용.
  4. 성공 → 모달 닫힘 + 토스트 "N건 저장됨"

유효성 검증

  • 입금금액: 양의 정수만 (음수·소수·0 불가)
  • 입금금액 > 현재미수금: 경고 후 사용자 확인 (위 §저장 동작 참조)

6 영수증 출력 자동 채움 로직

출력 대상 거래처 필터링 (날짜 D)

당일매출(D)전잔고(D)처리
= 0= 0출력 X
= 0> 0출력 X (사용자 확정)
> 0= 0출력 ✓ (전잔고 칸 빈 채로)
> 0> 0출력 ✓ (전잔고 칸 채움 + 총액 합산)

자동 채움 위치

'공급가 총액' 바로 윗 칸 (현재 비어있는 행):

  • 전잔고 > 0: "전잔고: {금액}" 표기
  • 전잔고 = 0: 그 행 그대로 빈 채

'공급가 총액' = 당일매출 + 전잔고

⚠ 출력 폼의 행 개수, 컬럼 폭, 디자인 절대 변경 X.

9 결정 사항 (확정 ✅)

모든 edge case 결정 완료.

  • Q1. ✅ 입금금액 > 현재미수금 — 경고 후 사용자 확인 (b)
    [저장] 클릭 시 입력값 > 현재미수금인 거래처가 있으면 경고 모달. "거래처 X의 현재 미수금은 18,000원입니다. 입력값 180,000원이 더 큽니다. 정말 저장하시겠습니까? [취소] [확인]" [확인] 시 정상 INSERT. 음수 미수금 허용(선입금/환불 대응). 구현 위치: FE 모달 저장 핸들러. BE는 단순 INSERT.
  • Q2. ✅ 입금 기록 수정/삭제 — 이번 범위 밖
    추후 별도 Apple. 이번 명세는 INSERT만.
  • Q3. ✅ 미래 날짜 입금 — 차단
    모달 날짜 입력란에 max=오늘. 직접 입력해도 검증으로 차단.
  • Q4. ✅ 같은 날짜 + 같은 거래처 두 번 입금 — 허용 (ii)
    DB UNIQUE 제약 X. 여러 row 누적 허용 (오전·오후 따로 받은 케이스 대응). SUM 계산이라 row 개수와 무관하게 일관됨.
  • Q5. ✅ 거래처 삭제 — soft-delete만
    기존 거래처마스터 정책 그대로. 입금기록 FK 유지.

11 검증 시나리오

TC-1. 첫날 매출 → 다음날 전액 입금
Given: 5/14 거래처 A 매출 18,000
When: 5/15 입금 18,000 전액 입력
Then: 5/15 영수증·집계표에 A 안 보임. 입금 모달에도 없음.
TC-2. 부분 입금 → 잔액 이월
Given: 5/14 B 매출 329,000
When: 5/15 입금 200,000 + 5/15 추가 매출 50,000
Then: 5/15 B 영수증 — 전잔고 129,000 / 매출 50,000 / 총잔액 179,000
TC-3. 매출 0 + 미수만
Given: 5/14 C 매출 54,000, 5/15 입금 0
When: 5/15 C 매출 없음
Then: 5/15 출력 안 됨. 5/16 [입금 입력]에 C 54,000 떠 있음.
TC-4. 입금 날짜 변경 (어제)
Given: 5/14 D 매출 10,000. 5/15에 입력
When: 모달 날짜를 5/14로 변경, 10,000 입력
Then: 입금기록(D, 5/14, 10,000) 저장.
TC-5. 입금금액 > 미수금 — 경고
Given: E 현재미수금 18,000
When: 사용자가 180,000 입력 후 [저장]
Then: 경고 모달 → [확인] 클릭 시 저장. 이후 E.현재미수금 = -162,000.

12 미수금 조정 (v1.2 추가)

배경

시스템이 계산하는 미수금과 실제 미수금이 다른 케이스 존재:

  • 시스템 도입 전 누적 잔액 (도원 케이스: 시스템 0 / 실제 3,400,000)
  • 외부 거래·구두 거래로 시스템 미입력 매출
  • 분쟁 조정·할인 등

워크플로우

  1. 입금 입력 모달의 각 거래처 행에 보라색 [조정] 버튼 ([전액] 우측)
  2. 클릭 → 별도 조정 모달 팝업
  3. "조정 후 금액" 입력 (사용자가 실제 미수금을 그대로 입력)
  4. 시스템이 차액 자동 계산: 조정액 = 입력값 − 현재미수금
  5. 차액 색상 표시 (+빨강 / -초록)
  6. [조정 저장] → adjustments 테이블에 row 추가 → 입금 모달 즉시 갱신

결정 사항 (사용자 확정)

  • 저장 방식: 별도 adjustments 테이블 (시안 A)
  • 입력 방식: 조정 후 금액 (시안 1) — 차액은 시스템이 계산
  • 사유/메모: 없음
  • 음의 조정: 허용 (시스템보다 적게도 가능)
  • 미수금 0 거래처 조정: 이번 범위 X (idea-box)

검증 시나리오

TC-6. 도원 시스템 미수금 → 실제 미수금 보정
Given: 도원 시스템 미수금 1,046,000
When: [조정] → "조정 후 금액" 3,400,000 입력 → 저장
Then: adjustments 테이블에 (도원, 오늘, +2,354,000) 저장. 모달 새로고침 시 도원 미수금 = 3,400,000.
TC-7. 음의 조정 (시스템 ↓ 실제)
Given: 거래처 X 시스템 미수금 1,000,000
When: 조정 후 금액 500,000 입력
Then: adjustments 에 (X, 오늘, -500,000) 저장. 현재미수금 = 500,000.
